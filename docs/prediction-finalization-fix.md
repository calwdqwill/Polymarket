# Исправление финализации 12h collector — 9 сентября 2026

## Наблюдения и причина отказа

Исходный collector: `research-20260909T151749Z`, рабочий PID `624`, время создания `18:17:49.370940 МСК`. Он не останавливался и не перезапускался. Плановый срок — 10 сентября `06:17:49 МСК`.

Полный исходный traceback сохранён рядом с dataset в `research-20260909T151749Z.analysis.stderr.log`. Сбой произошёл 9 сентября в `18:45:37 МСК`. Существенная часть стека старой версии:

```text
finish_prediction_research.py:64 -> finish(args.directory, args.wait)
finish_prediction_research.py:21 -> (path / "live.json").read_text()
pathlib.py:1027 -> self.open(mode='r', encoding=encoding, errors=errors)
pathlib.py:1013 -> io.open(...)
PermissionError: [Errno 13] Permission denied: '...research-20260909T151749Z\\live.json'
```

Подтверждённый программный дефект: finalizer каждые 5 секунд открывал меняющийся `live.json`, а первый отказ открытия завершал весь процесс ожидания. Collector публикует проекцию каждую секунду через `live.json.tmp` → `replace(live.json)`. Атомарность замены не гарантирует доступность открытия на Windows: режимы совместного доступа действуют до закрытия handles; переименование требует совместимости с delete sharing. См. [CreateFile — правила совместного доступа](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilea).

Вторая гонка: collector устанавливает STOPPED/FAILED **до** `journal.close()`, а итоговые metrics публикует **после** закрытия gzip. Одна терминальная проекция не служит барьером окончания записи.

Четыре read-only замера Windows Restart Manager (`RmRegisterResources`/`RmGetList`) для `live.json` и `live.json.tmp` вернули пустой список владельцев, код 0. Постоянной блокировки на момент диагностики нет. Известный publisher — PID 624; периодический reader — прежний finalizer. Кто именно держал конфликтующий handle при историческом отказе, по старому журналу установить нельзя: нет Win32-кода, владельца handle или трассы файловых операций. Гонка замены — рабочая гипотеза; участие OneDrive/антивируса не доказано. ACL и политики OneDrive не менялись. `RmShutdown`/`RmRestart` не вызывались.

## Исправление и границы

Выбран барьер завершения процесса вместо копирования активной проекции. Snapshot `live.json` сам требует открытия и не устраняет исходный конфликт; замена writer затронула бы ingestion. Изменён только отдельный finalizer:

1. Читает однократно опубликованный `run.json`: рабочий PID и время начала. Временные ошибки чтения повторяются ограниченно.
2. На Windows удерживает handle процесса с правами `SYNCHRONIZE | PROCESS_QUERY_LIMITED_INFORMATION`. Проверяет время создания против повторного использования PID. Пока процесс жив, не открывает `live.json`, manifest, metrics и raw.
3. После фактического выхода процесса проверяет терминальный статус, `segments.active=null`, список закрытых сегментов и принадлежность всех сегментированных gzip этому списку. `.tmp` не продвигается автоматически в источник. При незакрытом хвосте или неопубликованном финальном статусе анализ блокируется; оригиналы остаются для ручного восстановления.
4. Выполняет replay → analysis → REPORT. Несовпадение replay блокирует следующие этапы. Временные ошибки I/O повторяются каждые 0,5s до 60s; постоянная ошибка сохраняется с этапом и полным traceback. Публикация результатов проверяется: silent failure общего helper не считается успехом. REPORT публикуется через временный файл.
5. Собственная advisory-блокировка `finalization.lock` исключает два finalizer на dataset и освобождается ОС при выходе/аварии. Источники не удаляются и не перезаписываются; обновляются только производные артефакты. Повторный анализ допустим после устранения причины ошибки.

Предел ожидания — `stop_at + 10 минут`: зависший collector не останавливается, данные не открываются, finalizer сообщает FAILED. Это локальный процесс, не служба с восстановлением после reboot. Успешный replay будущих данных заранее не гарантируется.
